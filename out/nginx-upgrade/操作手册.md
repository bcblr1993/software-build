# nginx 升级操作手册

适用于现场已部署 sprixinSoft（v11 及同期版本）、需要把 nginx 换成 1.31.3 的场景。

整个过程**不修改现场任何既有文件**：新 nginx 装在自己的目录里，运行时指向
原有的配置和业务目录。旧程序原样保留，随时可以退回去。

---

## 一、包里有什么

| 文件 | 说明 |
|---|---|
| `nginx-1.31.3.tar.gz` | 新版 nginx 程序（约 4 MB） |
| `nginx.sh` | 启停脚本 |
| `操作手册.md` | 本文档 |

新 nginx 的情况：

- 版本 **1.31.3**
- 自带 OpenSSL 1.1.1w、PCRE2 10.44、zlib 1.3.1，**不依赖系统的这几个库**
- 在 glibc 2.17 基线上编译，凝思 6.0.80（glibc 2.19）及以上均可运行
- 编译模块只有 `--with-http_ssl_module --with-http_v2_module`，
  未编译 mp4、dav、mail、HTTP/3

---

## 二、开始之前

确认三件事：

**1. 用哪个用户。** 全程用现场运行 sprixinSoft 的那个普通用户，不要用 root。
本文档假设是 `sprixin`，安装目录是 `~/sprixinSoft`，请按实际情况替换。

**2. 现在的 nginx 是什么版本。**

```bash
cd ~/sprixinSoft && ./nginx/sbin/nginx -v
```

**3. 现在有哪些端口在服务。** 记下来，升级后要逐个核对。

```bash
netstat -antp 2>/dev/null | grep LISTEN | grep -E "90[0-9][0-9]|98[0-9][0-9]"
```

## 三、部署

### 步骤 1：解压新程序到独立目录

注意解压出来的目录名叫 `nginx`，与现场已有的同名，所以**先解到临时目录再改名**，
直接在安装目录下解压会覆盖现有的 nginx。

```bash
cd ~/sprixinSoft
mkdir -p /tmp/ngx-new && tar -xzf ~/nginx-1.31.3.tar.gz -C /tmp/ngx-new
mv /tmp/ngx-new/nginx ./nginx-1.31.3
rmdir /tmp/ngx-new
```

### 步骤 2：放入启停脚本

```bash
cp ~/nginx.sh ~/sprixinSoft/
```

此时目录结构应是这样（`nginx/` 是现场原有的，一个字节都没动）：

```
~/sprixinSoft/
├── nginx/              ← 现场原有：配置、html、业务目录、旧程序
├── nginx-1.31.3/       ← 新增：新版程序
├── nginx.sh            ← 新增：启停脚本
├── startup.sh          ← 现场原有
└── ...
```

### 步骤 3：先验配置，不启动

```bash
cd ~/sprixinSoft && bash nginx.sh test
```

看到 `test is successful` 才继续。若报错，错误信息里会写明文件和行号，
此时现场 nginx 仍在正常运行，没有任何影响。

### 步骤 4：切换

```bash
bash nginx.sh restart
```

脚本会先停掉正在运行的旧 nginx，再用新版启动。输出末尾会列出已监听的端口。

### 步骤 5：核对

```bash
bash nginx.sh status
```

把端口列表和步骤 2 记下的对照，应当一致。再抽查几个业务地址：

```bash
curl -s -o /dev/null -w "9000: %{http_code}\n" http://127.0.0.1:9000/
```

## 四、日常操作

全部在 `~/sprixinSoft` 目录下执行。

| 命令 | 作用 |
|---|---|
| `bash nginx.sh start` | 启动。已在运行时不会重复启动 |
| `bash nginx.sh stop` | 停止。优雅退出，处理完手头请求再走 |
| `bash nginx.sh restart` | 重启（停 + 启） |
| `bash nginx.sh reload` | 改完配置热加载，**不中断连接**，进程号不变 |
| `bash nginx.sh status` | 看运行状态、监听端口、程序路径、版本 |
| `bash nginx.sh test` | 只校验配置，不动正在运行的服务 |
| `bash nginx.sh version` | 看版本和编译参数（应对安全扫描时用得上） |

改了 `nginx.conf` 之后建议的顺序：先 `test` 确认语法，再 `reload` 生效。
`reload` 在配置有误时会拒绝加载，正在运行的服务不受影响。

## 五、退回旧版本

旧程序 `nginx/sbin/nginx` 一直都在，没有被删也没有被覆盖，配置和业务目录也
全程未动，所以退回只是换个程序跑。

**最简单的办法**，就用原来那条命令：

```bash
cd ~/sprixinSoft
bash nginx.sh stop
sh startup.sh 2
```

`startup.sh 2` 本身会先清掉在跑的 nginx 再启动旧版，所以即使忘了先 `stop`
也能退回去。

若想显式执行，等价于：

```bash
cd ~/sprixinSoft
bash nginx.sh stop
export LD_LIBRARY_PATH=$PWD/nginx/lib:$LD_LIBRARY_PATH
$PWD/nginx/sbin/nginx -c $PWD/nginx/conf/nginx.conf -p $PWD/nginx -e $PWD/logs/nginx/error.log
```

退回后确认：

```bash
./nginx/sbin/nginx -v            # 应显示 1.27.4
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:9000/
```

## 六、注意事项

### 换用 nginx.sh 后，不要再用 startup.sh 管 nginx

旧的 `startup.sh` 在启动 nginx 前会执行

```bash
ps -ef | grep nginx | grep -v grep | awk '{print $2}' | xargs kill -9
```

它会把新 nginx 一并杀掉，然后拉起旧版。所以：

- **不要**再执行 `sh startup.sh 2`
- **不要**再执行 `sh startup.sh all`（里面包含 nginx）

redis、nacos、influxdb、rabbitmq 照旧用 `startup.sh` 单独启停，只有 nginx 走
`nginx.sh`。

### 机器重启后需要手工拉起

本脚本不接管开机自启。若现场配置了开机自动执行 `startup.sh all`，重启后起来的
会是旧 nginx，需要执行一次 `bash nginx.sh restart` 换回新版。

## 七、常见问题

### 报"找不到新 nginx 程序目录"

脚本没找到 `nginx-1.31.3/sbin/nginx.bin`。确认步骤 1 的目录改名做了，
或直接指定：

```bash
NGX_HOME=~/sprixinSoft/nginx-1.31.3 bash nginx.sh status
```

### 报"找不到 nginx 配置目录"

脚本按 `nginx/conf/nginx.conf` 查找。若现场目录名不同，显式指定：

```bash
NGX_PREFIX=~/sprixinSoft/你的nginx目录 bash nginx.sh start
```

### 启动后某些端口没监听

先看错误日志，路径在 `status` 输出里有：

```bash
tail -30 ~/sprixinSoft/logs/nginx/error.log
```

常见原因是端口被别的进程占着——先 `netstat -antp | grep <端口>` 看是谁。

### 访问静态页面返回 403

nginx 的 worker 以 `nobody` 身份运行，安装路径上任何一级目录缺少其他用户的
执行权限，都会导致读不到文件。逐级检查并补上：

```bash
chmod o+x <对应目录>
```

### 页面能开但 HTTPS 报证书错误

新版自带 OpenSSL 1.1.1w，不再使用系统的 OpenSSL。证书文件本身不受影响，
若有问题请检查 `nginx.conf` 里证书路径是否为绝对路径。

## 八、应对安全扫描

现场扫描器报出的 nginx 漏洞，多数是**因为读不到版本号而按最坏情况全部列出**。
现场 `nginx.conf` 里有 `server_tokens off`（去除中间件版本号），扫描器只知道
这是 nginx、不知道具体版本，于是把库里所有 nginx 漏洞都报了出来。

**注意：仅仅升级版本不会让这份报告变干净**，因为扫描器依然读不到版本。

申诉时可用的材料：

```bash
bash nginx.sh version
```

输出包含确切版本与编译参数。对照 nginx 官方安全公告
<https://nginx.org/en/security_advisories.html> 逐条核对即可。

以 1.31.3 为例，此前扫描报告中列出的漏洞对照如下：

| CVE | 官方修复版本 | 1.31.3 是否受影响 |
|---|---|---|
| CVE-2026-48142 | 1.31.2+ | 否 |
| CVE-2026-9256 | 1.31.1+ | 否 |
| CVE-2026-42945 / 42946 / 42934 / 40701 | 1.31.0+ | 否 |
| CVE-2026-27654 / 27651 / 27784 / 32647 / 28753 | 1.29.7+ | 否（且相关模块未编译） |
| CVE-2026-1642 | 1.29.5+ | 否 |
| CVE-2025-53859 | 1.29.1+ | 否（mail 模块未编译） |
| CVE-2025-23419 | 1.27.4+ | 否 |
| CVE-2024-7347 | 1.27.1+ | 否（mp4 模块未编译） |

其中涉及 mp4、dav、mail 模块的几条为双重不成立：版本已高于修复版本，且这些
模块在编译时就没有包含进来，可用 `bash nginx.sh version` 的输出佐证。

若扫描方要求自证版本，可临时把 `server_tokens off` 改为 `on` 重扫一次，
让扫描器读到 `nginx/1.31.3` 做版本过滤，扫完再改回。这与"不得暴露版本号"
的要求存在冲突，需与安全人员沟通确认。
